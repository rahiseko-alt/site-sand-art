# 0001 スジャータの物理計算は1/60秒の固定刻みで回す

## 背景

収束時間を変えるたびに、収束後に粒子がカクカク・プルプルする問題が繰り返し起きていた。

原因は `site/demo.html` の `renderLoop` で、基準の違う計算が混ざっていたこと。

- 戻りバネの強さ `pull = 93.75 * dt` は**フレーム時間に比例**していた
- 位置の更新 `s.x += s.xv`、粒子の減衰 `*= 0.4`、流体の減衰 `*= 0.99` は**フレーム回数**で効く

1フレームで目標位置に引き戻す強さを k（= 係数 × 刻み時間）として1次元で整理すると、
`v' = v + k(ox - x)`、`x += v'`、`v = 0.4 v'` となる。この式は **k > 2.8 で発散**する。

- 係数 93.75 のとき、発散の境目は1フレーム **29.87ms**。修正前の実測は最大 27.9ms で、余裕は約2msしかなかった
- 収束を速くしようと係数を上げると境目が縮み、普段のフレームでも発散 → プルプルになる
- 実測：1フレームを25ms重くすると、収束後の1フレームの移動は平均 1.4px、最大 8px

## 決定

- 物理計算（流体・戻りバネ・粒子の移動）は `PHYSICS_STEP = 1/60` の固定刻みで回し、バネにも `PHYSICS_STEP` を使う。
  k は常に `93.75 / 60 = 1.5625`
- **1フレームにつき計算は最大1回**（`MAX_PHYSICS_STEPS = 1`）。140k粒子の計算1回が1フレーム分近くかかるため、
  遅れを取り戻そうと複数回回すと、さらに重くなって悪循環になる（実測：フレーム時間の中央値 17.6ms → 59.7ms）
- フレーム時間を刻みに割り当てる判定は四捨五入（半刻み以上で計算1回）。60Hz で計算0回のフレームが出ないようにするため
- ポインタの入力、色の補間、画面の傾きはこれまでどおり毎フレーム処理する

## 結果

- 1フレームを25ms重くしても、収束後の1フレームの移動は 0.000px
- 収束時間は約5.5秒（修正前は約6.2秒）
- 重い環境では、揺れる代わりに動きが少しゆっくりになる

## 今後の調整のルール

- **収束時間を変えるときは、k = 係数 × (1/60) が 2.8 を超えないこと（絶対条件）**。
  行き過ぎを抑えるなら 2.0 程度まで（係数で約120まで）が目安
- k が 1.5 前後のとき、バネは毎フレーム行き過ぎて逆側に振れながら止まる。強めるほど行き過ぎも大きくなる
- 速さ（0.5）でバネをリセットする判定（`returnStartAt`）があるので、揺れが大きいと「止まる → 跳ねる」を繰り返しやすい
- 流体の減衰（0.99）は、バネが発散するかどうかの条件には入っていない。ただし収束時間そのものには効く
- 調べるときの道具（`tools/sujata/`。`node server.js` を起動した状態で実行する）
  - `spring_model.py`：k ごとの安定性を計算する
  - `jitter_diag.py [重くするms]`：収束後の揺れとフレーム時間を実測する
